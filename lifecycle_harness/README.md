# AudioService lifecycle harness

A standalone Flutter app, separate from `audio_service/example`, that runs Android
instrumentation tests against the local `audio_service` checkout. It uses the plugin's own
`AudioServiceActivity`, `AudioService`, and `MediaButtonReceiver` directly. `lib/main.dart` only
calls `AudioService.init` with a handler that never plays and then shows a placeholder widget.

## What `AudioServiceLifecycleTest` checks

The test exercises the last-client-unbind path without killing the application process. Each
cycle launches `AudioServiceActivity`, waits for a new `AudioService` to be created, closes the
Activity, waits for that service's `onDestroy` to complete, and launches again.

The test asserts this invariant:

```text
AudioService may be destroyed and recreated within the same process,
but the FlutterEngine generation must stay the same.
```

Every observed service object is kept in an identity set, and the test asserts all three of:

```text
same process PID
multiple distinct AudioService instances
one FlutterEngine generation
```

`flutterEngineGenerationSurvivesServiceRecreationInSameProcess` (`@MediumTest`) performs 3
recreations. `flutterEngineGenerationSurvivesOneHundredServiceRecreationsInSameProcess`
(`@LargeTest`) performs 100 recreations with the same assertions on every cycle.

### Timing dependency

The fix defers engine disposal by `AudioServicePlugin.ENGINE_DISPOSAL_DELAY_MS` (1000 ms). When the
Activity comes back, `getFlutterEngine()` cancels any pending disposal. The harness relaunches
about 25 ms after `service_destroy_end`, so it always lands inside that window. If the relaunch
comes later than the delay, the fix disposes the engine, which is intended behavior when no client
returns, and the "one generation" assertion fails. See the results below.

## Toolchain

The app was generated by `flutter create` on Flutter 3.47.4 and uses the declarative
Flutter Gradle plugin, AGP 9.1.0, Kotlin 2.4.0, Gradle 9.3.1, and JDK 17. The AndroidX Test
dependencies are Core 1.6.1, Runner 1.6.2, and ext-JUnit 1.2.1. `pubspec.yaml` overrides
`audio_service_platform_interface` and `audio_service_web` with their local paths, so the whole
checkout is tested as one coherent set of packages.

## Commands

From `lifecycle_harness/`, with an emulator running (the examples use `emulator-5554`):

```bash
flutter pub get
flutter build apk --debug   # also generates the ignored Gradle wrapper files
cd android
adb -s emulator-5554 logcat -c
./gradlew :app:connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=com.ryanheise.audioservice.AudioServiceLifecycleTest
adb -s emulator-5554 logcat -d -s AudioServiceLifecycle:W AndroidRuntime:E TestRunner:I
```

To run one variant, append `#flutterEngineGenerationSurvivesServiceRecreationInSameProcess` or
`#flutterEngineGenerationSurvivesOneHundredServiceRecreationsInSameProcess` to the class name.

## Results

Device: `emulator-5554`, AVD `Phone_Screenshots`, Android 16 / API 36. Flutter 3.47.4.

### Baseline: `minor` @ `02fabf8` fails as expected

Both tests fail on the first recreation:

```text
java.lang.AssertionError: FlutterEngine generation changed during service recreation cycle 1
expected:<1> but was:<2>
```

The PID stays the same, but `AudioService.onDestroy()` destroys the engine inline and the relaunch
creates a new one:

```text
event=flutter_engine_create_begin generation=1 requester=activity
event=service_create_end serviceGeneration=1 engineGeneration=1
event=flutter_engine_destroyed generation=1
event=service_destroy_end serviceGeneration=1
event=flutter_engine_create_begin generation=2 requester=activity
event=service_create_end serviceGeneration=2 engineGeneration=2
```

### Fix: `claude/audio-service-ownership-reconnect-6x2z0s` @ `432b305` passes

`2 tests, 0 failed`. There were 105 `service_create_end` events (4 + 101), exactly one
`flutter_engine_create_begin`, and no `flutter_engine_destroyed`. In each cycle the disposal is
scheduled and then cancelled when the Activity returns:

```text
event=flutter_engine_dispose_scheduled generation=1 delayMs=1000
event=service_destroy_end serviceGeneration=1
event=flutter_engine_dispose_cancelled generation=1 reason=engine_requested_by_activity
event=flutter_engine_reused generation=1 requester=activity
event=service_create_end serviceGeneration=2 engineGeneration=1
```

### Probe: relaunch after the disposal delay fails on the fix

This probe is not part of the committed test. A temporary `SystemClock.sleep(1500)` was added
between closing the Activity and relaunching it. The fix branch then fails with the same
`expected:<1> but was:<2>`. The engine is disposed after 1000 ms and the relaunch creates
generation 2. The fix removes engine churn only for relaunches that start within the delay window.
